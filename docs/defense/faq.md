# 常见问题（FAQ）

## Q1：为什么用单工作流而不是多 Agent？

多 Agent 让「模型决定调用哪个工具」，模型就成了规则的解释者，存在绕过规则、编造数值的风险。本项目推荐流程固定七步，分类器只能调用已写好的服务；营养数字全部由后端计算，LLM 只把结果组织成自然语言，且 post_validate 核对数字是否在后端允许集合内。

## Q2：模型会不会编造营养数字？

不会。GI、热量、碳水等数字由后端从成分表计算并写入响应，LLM 输入里只有已算好的数字，输出还要经过 post_validate 过滤——凡是不在允许集合内的数字整条回答回退为模板。

## Q3：关键词拦截能拦住所有风险问题吗？

不能。关键词拦截能拦住常见说法（用药剂量、诊断、胸痛、低血糖、肾病、妊娠、未成年、常见降糖药名），但换一种说法可能漏过。因此还有两层兜底：营养数字始终由后端计算，模型不输出治疗或用药建议；回答末尾固定附免责声明。

## Q4：云 LLM 不可用怎么办？

推荐降级为模板解释；问答回退本地 Ollama qwen2.5:7b，仍失败则提示稍后重试。健康检查会把 llm 标为 down。

## Q5：检索为什么用 bge-m3 嵌入模型？

bge-m3 支持中文且是多语言嵌入模型，适合中文《食养指南》切片做语义检索；Chroma 做向量存储，本地部署无需外网。

## Q6：数据分别存在哪？

结构化数据（档案、冰箱、食谱、计划、购物、会话）在 PostgreSQL；食材-疾病-食谱关系在 Neo4j 图谱；指南切片向量在 Chroma。三者通过食材名/用户 id 关联。

## Q7：安全边界是什么？

本系统只做饮食参考，不提供用药剂量、疾病诊断、急症处理、肾病/妊娠/未成年个体化食谱。空腹血糖和糖化血红蛋白只记录、不参与推荐计算。

## Q8：项目复现成本高吗？

后端 FastAPI + PostgreSQL + Neo4j + Chroma + 本地 Ollama，都可 Docker 化；前端 Vue 3。除云 LLM 需申请 Key 外，其余均可本地部署。
